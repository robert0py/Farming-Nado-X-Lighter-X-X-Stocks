# Публикация без данных владельца

Проверка подготовки публикации: 29.10.2026. Область проверки — утечки пользовательских credentials и торговых данных в распространяемом проекте; это не полный аудит безопасности бирж или торговой стратегии.

| Проверка исходников и истории | Подтверждённых утечек |
| --- | ---: |
| Ключи и токены: Gitleaks, все ветки и теги, 75 предшествующих коммитов | 0 |
| Совпадения с сохранёнными ключами, адресами аккаунтов, signer и токеном управления | 0 |
| Отслеживаемые хранилища, базы, конфигурации аккаунтов и торговые отчёты | 0 |

Для сопоставления пользовательские значения читаются только локально в памяти. Они не включаются в этот документ, результаты публичных тестов или конфигурацию CI. Публичная ссылка на правила xPoints не является пользовательским секретом. Хеши GitHub Actions и искусственные значения из изолированных тестов не являются ключами подключённых аккаунтов.

Существующие релизы перед открытием репозитория проверяются отдельно: скачивание EXE, распаковка CArchive и вложенного PYZ, поиск известных пользовательских значений в содержимом и описаниях релизов. ZIP с торговыми отчётами и локальные журналы не являются дистрибутивами и не публикуются.

## Что получает другой пользователь

- Исходники или Windows EXE, созданный в чистом GitHub Actions runner из исходников и зависимостей.
- Пустые подключения при первом запуске у нового пользователя ОС. Никаких готовых аккаунтов, signing keys или истории владельца проекта.
- Собственное локальное зашифрованное хранилище после настройки. Обычный повторный запуск сохраняет собственные подключения этого пользователя.

Windows: `%LOCALAPPDATA%/HedgeBot/state`. Linux: `~/.local/share/hedge-bot`. Переопределение `HEDGE_STATE_DIR` выбирает собственную папку состояния. Эти папки, `.env`, ключи и выгрузки не должны попадать в репозиторий или распространяемый архив.

## Проверки перед новой публикацией

1. Запустить `python scripts/check-publication.py`: приватные runtime-файлы в списке Git блокируют сборку. Проверка не читает пользовательское хранилище.
2. Проверить всю историю на секреты, включая удалённые файлы и теги, например `gitleaks git --redact --log-opts="--all"`.
3. Проверить готовые дистрибутивы и заметки релизов, выполнить тесты и offline self-check сборки. Реальные ключи не передавать в CI.
4. Если секрет обнаружен, держать репозиторий закрытым, отозвать соответствующий ключ и очистить все содержащие его доступные версии, теги и вложения. Удаления строки только из последнего коммита недостаточно.

Сканер выявляет известные значения и поддерживаемые шаблоны; отсутствие находок не является гарантией обнаружения любого возможного секрета. При изменении состава дистрибутива проверку нужно повторить.
